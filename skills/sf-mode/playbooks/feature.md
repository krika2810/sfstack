# Playbook: Feature

New or changed behavior, built from a named data shape. The shape comes first, the design second, the code third. Every step ends in something a reviewer can check.

## Steps

1. **Name the data shape.** Before any code, write down the objects, fields, and relationships the feature touches, existing or new. Apply **principle-model-the-domain**: one clear structure instead of scattered conditionals. If the feature needs new schema, this step produces the object and field definitions, not the Apex.
2. **Ground in what exists.** Run **sf-how** over every automation that already touches those objects: triggers, record-triggered flows, validation rules, duplicate rules, entitlement or assignment rules. A feature that ignores the existing order of execution will fight it in production.
3. **Design before code.** If the feature crosses an object or class boundary, run the **sf-architect** skill. For a genuinely novel design, run **sf-arena** to compare two or three shapes in separate scratch orgs and let evidence pick.
4. **Build the verification harness.** If the project has a project-local verification skill (generated by **sf-create-verification-skill**), use it. Otherwise create a scratch org, deploy, and prepare the seed data the feature needs:
   ```bash
   sf org create scratch --definition-file config/project-scratch-def.json --alias feature-x --duration-days 7
   sf project deploy start --source-dir force-app --target-org feature-x
   sf data import tree --plan data/seed-plan.json --target-org feature-x
   ```
5. **Write the failing tests first** per the **sf-tdd** skill: one test per behavior the feature promises, bulk and single-record paths both, real transaction semantics with `Test.startTest()` and `Test.stopTest()`.
6. **Implement in small ordered commits.** Schema first, then Apex, then Flow or LWC, then tests passing. Each commit deploys clean and keeps the suite green. Apply the principles as they bite: bulkify by default, selective queries, explicit access, no hard-coded IDs.
7. **Drive the feature like a user.** Apex tests are not the feature. Open the org (`sf org open --target-org feature-x --path /lightning/o/Order__c/list`), click through the Lightning page, and capture a screenshot or the record state that proves the behavior end to end. For an LWC, run the Jest suite too:
   ```bash
   npm run test:unit
   ```
8. **Adversarial review.** Run **sf-interrogate** on the diff before shipping: bulk safety, CRUD/FLS and sharing, SOQL selectivity, transaction and async design, test quality.
9. **Run Opening a PR** (`opening-a-pr.md`).

## Gotchas and failure modes

- **Schema by accident.** Fields created on the fly during Apex work end up with wrong types, no help text, and no FLS. Schema is a deliberate first step with **principle-metadata-is-code**, and it ships in the same source tree as the code.
- **The feature works in system mode only.** If the running user cannot see the records because of sharing, the feature does not exist for them. Test as the intended user with `System.runAs`, and state the access decision (`with sharing`, `stripInaccessible`) in the work. On API version 67.0 and later, Apex runs in user mode by default, which makes missing FLS show up earlier: https://developer.salesforce.com/docs/atlas.en-us.apexcode.meta/apexcode/apex_security_sharing_chapter.htm
- **Volume blindness.** The demo runs on ten seed records. Production has two million. If the feature scans, sums, or updates at scale, that is an async design question from step 1, not a performance bug later. See **principle-async-for-volume**.
- **Automation collisions.** A new after-save flow on an object that already has a trigger and a workflow rule changes the order of execution for everyone. Check what exists before adding, per **principle-subtract-before-you-add**.

## Proof it worked

- Test-run ID for the full local suite in the feature scratch org, all green, with coverage per class.
- The driven behavior: screenshot, or the record queried after the drive showing the expected field values.
- The deployment ID of the final deploy to the scratch org (starts with `0Af`).
- For LWC, the Jest output with pass counts.

## Reply

What the feature does for its user in one plain sentence, the data shape it introduced, the evidence (test-run ID, deployment ID, screenshot), and the design decisions an owner inherits.
